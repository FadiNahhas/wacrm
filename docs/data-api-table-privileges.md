# Explicit Data API table privileges

Review baseline: `FadiNahhas/wacrm` main at
`750e833639a385a8c8fe8395d76938f8cf753865`, confirmed on 2026-10-28.
41 existing migrations create 36 public application tables. The only existing
table/column grant is `notifications.UPDATE(read_at)` in 027; other grants are
function EXECUTE grants.

Supabase's [rollout notice](https://github.com/orgs/supabase/discussions/45329)
and [Data API security guide](https://supabase.com/docs/guides/api/securing-your-api)
require explicit table grants when automatic exposure is disabled. The October
30 change affects newly created tables; existing tables keep their ACLs. Grants
allow an operation; unchanged RLS policies still decide which rows a session can
access. `service_role` bypasses RLS but still needs table privileges.

## Scope and compatibility

This is an additive migration for review. No hosted database was accessed.
It does not change policies, RLS flags, schema exposure settings, function ACLs,
default privileges, or existing grants. It is safe to replay. Consequently an
existing deployment can retain broader historical ACLs; this is not an ACL
normalization or revocation migration. The exact matrix below describes a fresh
schema with automatic table grants disabled, plus the column grant from 027.

`createClient` from `lib/supabase/server` and `requireRole` / `getCurrentAccount`
use the caller's authenticated session, even in server routes. API-key contexts
and `supabaseAdmin()` use `service_role`. Shared helpers were traced to their
callers, including the dashboard send core, tag resolution and AI ingestion.
Embedded PostgREST reads and RLS parent joins also require SELECT on related tables.

No application table needs `anon` access. The anonymous invitation peek stays
behind its existing definer RPC. No application sequences exist (UUID IDs).
TRUNCATE, REFERENCES, TRIGGER and grant options are not added.

## Deliberate boundaries and review decisions

- Presence and notification insertion still run under their existing definer
  functions. The profiles guard from 034 continues to reject direct membership
  changes. No grants are added merely to let a definer function write.
- Quick-reply, automation and flow mutations use checked service-role routes.
  Their broader RLS policies do not justify adding unused session write grants.
- AI knowledge ingest's comment says service-role, but the POST/PATCH/reindex
  callers actually pass their session client. Those paths need authenticated
  chunk SELECT/INSERT/DELETE. A comment must not override the call sites.
- Unused policy capabilities are deliberately withheld on a fresh install,
  including session writes to webhook_endpoints, profile INSERT, hard DELETE of
  API keys, and UPDATE of tags/notes/chunks. Existing deployments retain any
  prior grants. If undocumented direct clients depend on these operations,
  confirm their role and operations before adding grants. No such requirement
  was inferred from the current code.
- Existing broad function execution and previously granted ACLs are outside
  this compatibility patch. This matrix is not a claim that RPCs cannot perform
  additional operations. A separate audit would be needed to change that surface.

## Validation

The migration CI job injects `supabase/ci/no-table-defaults.sql` as a temporary
first migration in its disposable local database, then replays every real
migration and checks the complete role/table matrix. The test fixture revokes
only table defaults; function/storage behavior is unchanged. It is not part of
the deployable migration directory. The verifier checks RLS flags, every S/I/U/D
grant, absence of destructive privileges and anon access, notification column
grants, and representative cross-account/RPC/trigger behavior. Fixture rows are
rolled back using a subtransaction, including on failures.

Run the updated Migrations workflow in an isolated environment with Docker and
the pinned Supabase CLI before approval. No live migration, push or deployment
is part of this patch. Local review execution results are recorded separately
with the delivered patch.

For future tables, add explicit per-role grants alongside table creation and
RLS in the same migration, and extend the assertion matrix with the required
operations. Do not restore automatic grants as a workaround.
